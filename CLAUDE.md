# CLAUDE.md
Guidance for Claude Code (and humans) working in this repo. **Keep this file and MEMORY.md token-efficient: dense, minimal blank lines, no filler; lines may exceed 80 chars. Apply the same when editing them.**

## Session protocol (read first)
- **Start:** a **SessionStart hook** (`.claude/settings.json`) prints `HANDOFF.md` into context by itself; no print means no handoff. Then check MEMORY.md "TODO / open questions".
- **HANDOFF.md rule:** whenever a turn ends needing **human action** (owner-side migration/deploy/smoke-test, a decision, subagent output awaiting review), write/overwrite `HANDOFF.md`: ① what was done this session, ② exact pending human steps (commands verbatim), ③ how a fresh session resumes (files/memory entries to read). Purpose: owner can clear context and start a new session from it. Gitignored; superseded by the next handoff.
- **Load the skill before you edit the area:** `spa-frontend` for anything in `worker/public/`, `worker-backend` for `worker/worker.js`, `worker/src/*`, the migrations or the SQL. They hold the constraints that used to live in this file; do not re-derive them from the code.
- The big files are `worker/public/app.js`, `worker/src/api.js` and MEMORY.md — read targeted sections, not the whole file, when you know what you need. `MEMORY-ARCHIVE.md` is retired history; leave it closed unless the question is why something used to work that way.

## Communication style (how to talk to the owner)
Owner holds a **BS in Management Information Systems**. Bridge IT and strategy: frame a technical trade-off as system integration, scalability, data flow or value. Do not over-explain foundational tech and do not walk through low-level syntax.
**Write in Simplified Technical English (ASD-STE100 spirit, not the strict standard) — chat prose, commit messages, docs. README.md keeps the strict version (see its own rule).**
1. Use active voice. Write "The system sends the file", not "The file is sent by the system". 2. Put one idea in each sentence; split a sentence that has two. 3. Keep sentences short — no word count, but cut every word that adds nothing. 4. Use a maximum of three words in a noun cluster: "the log of failed jobs", not "the failed job log record". 5. Use one term for one thing — if it is a "data pipeline", it is never later a "data flow" or an "ingestion path". 6. Use one meaning for each word; do not use "run" for both execute and manage. 7. Start an instruction with the verb: "Open the panel", not "The panel must be opened". 8. Expand an acronym at first use only. 9. Use lists for steps and comparisons; use prose for reasoning.

## Project overview
**FinanceTracker** is a **personal finance tracker**. Since **v2.0.0 (2026-08-23) the backend is a Cloudflare Worker over Cloudflare D1** — one Worker serves the PWA, the JSON API, the Telegram bot and two cron jobs. Google Sheets is gone as the source of truth (frozen archive; the v1 backend is `git show v1.9.2:Transactions.gs` etc.).
- **Three ways in, one set of handlers:** the **PWA** (`worker/public/`), the **Telegram bot** (`worker/src/telegram.js`), and **Gmail ingest** (Apps Script courier → `?action=ingestEmail`). All route through `worker/src/api.js`.
- **What is left in Apps Script:** `Gmail.gs` (mail courier, 5-min trigger) and `Backup.gs` (nightly dump into a spreadsheet). **No Web App deployment, no `doGet`/`doPost`, no `deploymentId`, no `GAS_URL` secret.** `GmailApp` is the only reason GAS survives at all — free OAuth to the owner's mailbox with no off-platform equivalent.
- **Locale:** amounts in **PHP**; timezone `Asia/Manila`.
- **History:** v1 (GAS + Sheets, v1.0.0→v1.9.2) is the design record — `git show v1.9.2:CLAUDE.md` for the sheet-era lore, `git show v1.3.4:OVERHAUL_PLAN.md` for the original overhaul. The v2 cutover is done and its one-shot kit is deleted — `git show v2.3.1:D1_MIGRATION.md` for the execution plan, and the same for `Export.gs`, `migrate/import.js`, `migrate/verify.js`.

## Git workflow (gitflow + releases)
- **`main`** = released/live code only. **`develop`** = integration branch; day-to-day commits and merges land here.
- **Features:** `feature/<name>` off `develop`, merge back to `develop`.
- **Release: a merge into `main` is the ONLY way code reaches live.** `.github/workflows/release.yml` runs on that merge — `npm test`, D1 migrations, `wrangler deploy`, tag `v<package.json version>`, GitHub Release, in that order (new code must never meet an old schema). A push to `main` whose version is already tagged does nothing, so the hotfix flow reaches live on the bump commit. **No credential is needed locally any more**; the Cloudflare token lives in GitHub repo secrets.
- **Preparing a release:** bump on `develop` (`npm version patch|minor --no-git-tag-version`, commit) — **and hand-edit `worker/public/index.html`'s `brand-ver` span to match in the same commit**: `npm version` does not stamp it, and `test.js` fails when the two disagree. Then `npm run release`, which **does not release** — it checks the bump, runs the tests and opens the `develop` → `main` PR. Merging that PR ships.
- **Hotfix:** `hotfix/<name>` off `main` → merge to `main`, bump patch, then **back-merge `main` → `develop`**. The workflow releases on the bump commit.
- **Tags/Releases invariant:** every tag is `vX.Y.Z`, on `main`, created only by the Release workflow, with a matching GitHub Release. Never hand-create tags or Releases.
- Push `develop` freely; never push directly to `main`. The push hook enforces both.
- **Worktrees** (`git worktree add .claude/worktrees/<name> -b <branch>`) let a hotfix run beside unfinished `develop` work with nothing stashed. **Run `npm run bootstrap` inside a new one before anything else** — `node_modules`, `worker/.dev.vars` and the dev port are all gitignored, so a worktree inherits none of them. Never run `npm run release` from a worktree, and remove one when its branch merges. `.claude/worktrees/` is gitignored.

## Conventions & gotchas
- **Never commit credentials** or any URL/id that acts as one. `.clasp.json` (`scriptId` only) is safe; `worker/.dev.vars` and `.clasprc.json` are gitignored.
- **Every "today" goes through `manilaToday()`.** A defaulted transaction date and the BIR quarter window are the two places a UTC slip silently corrupts data.
- **Month keys are `yyyy-MMM` with exactly that capitalisation, everywhere.**
- **The Growth segment rides the FUNDING transfer** (Wise→IBKR, category `Investment: Growth`, budget Monthly $200 = "did I park this month's $200"); broker buy legs (IBKR→ticker/IB01) and EF parking are `Transfer: Internal` — tagging both legs double-counts budget actuals. **There is deliberately NO Stability category or budget row** (removed 2026-08-26): EF accrues as unspent residue, which a monthly meter can't track — the Emergency-runway card is the only EF measure. The convention lives in the category DESCRIPTIONS (which the Gemini prompt inlines, so the bot follows it); `getInvestments`' pulse derives buys from share-priced accounts, not categories, so it needs no discipline. Runway = the `isInvestedNetWorth` liquid side minus receivables minus credit.
- **A UI-only change is not live until the Worker redeploys** — `worker/public/` ships with the Worker, so it rides the same release as backend code; there is no separate asset upload. Nobody runs `wrangler deploy` by hand any more, the merge into `main` does it. A GAS change is the exception: `npm run push` from the owner's machine and nothing else (no deployment exists, and clasp needs interactive OAuth, so no session can do it).
- **Accounting conventions (v2.5.0/v2.6.0, from the accounting-soundness review).** ① **A refund is a NEGATIVE-amount Expense row in the ORIGINAL category** — never `Income: Other`, which overstated both sides. ② **Reports are sign-aware**: budgets, dashboard spend/flow and the runway's average spend sum `amount_php_u` signed, never `ABS()`, so a refund nets its category down; Telegram's `querySummary` keeps `ABS` on purpose ("how much moved"). ③ **A cross-currency transfer that lands in PHP stamps the IMPLIED rate** (`ToAmount/Amount`), not the live rate — the live rate hid the conversion spread; an explicit `ExchangeRate` still wins. ④ **The month close is yesterday's month**: the cron stamps `monthOf(manilaYesterday())`, so the run on the 1st closes the previous month with its last day in it. ⑤ **A negative receivable is a liability** — it reports under liabilities and shortens the emergency runway; a positive one is neither (money lent is not reachable). ⑥ **`liabilities` is NEGATIVE everywhere** — API, `nw_snapshots`, `netWorthTotals`; only the SPA hero absolutes it. ⑦ **`amount_u` is never zero** — rejected on every write path AND a DB CHECK since `0003_tx_checks.sql` — but it may be negative. ⑧ **The `transactions` invariants live in the SCHEMA (v2.6.0):** `amount_u != 0`, `(to_account_id IS NULL) = (to_amount_u IS NULL)`, `fx_rate IS NULL OR fx_rate > 0`, and a real month/day in `date`. A `wrangler d1 execute` escape hatch now fails on a bad shape too — that is the point. The migration recreates the table (SQLite cannot add a CHECK in place); it **copies the rows FIRST**, so a row that breaks a CHECK aborts it with the live schema untouched.
- **A new pure helper gets a test in `test.js`;** anything touching SQL or a handler gets one in `test-api.js`; a new invariant whose failure is silent gets a contract guard. (The push hook already runs `npm test` for you.)
- Keep **MEMORY.md** current: decisions, trigger setup, secret locations.
- **Keep README.md current whenever a change touches the human's world** — a new/renamed secret or `meta` key, a new trigger or schedule, a new hosted service, a changed deploy/migration step, a new manual setup, a new failure mode worth a troubleshooting row, or a stack change. Pure code/refactor/UI-behaviour changes need nothing. Same commit as the change. **Public repo: names of secrets, never values or URLs.**
