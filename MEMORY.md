## Project facts
- **What:** personal finance tracker. **Since v2.0.0 (2026-08-23) the backend is a Cloudflare Worker over Cloudflare D1.** Google Sheets is a frozen read-only archive, not the source of truth.
- **Cloudflare Worker:** `financetracker-telegram` (free plan) — serves the PWA, `/api` (D1), the Telegram bot at `/tg`, and two cron jobs. **Never rename it:** `name` is the `.workers.dev` subdomain, i.e. both the app URL and the webhook target. Deployed from `worker/` with `npx wrangler deploy` (also run by `npm run release`).
- **D1 database:** `financetracker`, region `apac`. Schema in `worker/migrations/`. Money is **integer micros**; month keys are `yyyy-MMM`; balances are computed at read, never stored.
- **Apps Script ID:** `1IiUkd6dyJFnLuGXjjcS_CEohyeZLsXNO3eqFGm438IQL02dyhUxjgarE` (linked via `.clasp.json`). **No Web App deployment any more** — two trigger-driven files only (`Gmail.gs` courier, `Backup.gs` nightly dump). `GmailApp` is the sole reason GAS survives.
- **Frontend:** the PWA in `worker/public/` — 7 screens (Dashboard · Transactions · Budgets · Accounts · Swap · Tax · Admin), offline-capable since v1.6.1. The `/api` JSON contract did not change at the D1 cutover, so `app.js` was untouched apart from the Admin screen.
- **Locale:** PHP; timezone `Asia/Manila`. Every "today" goes through `manilaToday()` — Workers and D1 run in UTC.
- **Daily interest:** `gross = balance * rate / 365`, minus **20% withholding tax**, posted as `Income: Interest` for accounts with `interest_frequency = "Daily"`. Cloudflare cron, 00:30 Manila.
- **Share prices:** IBKR Flex Web Service, Cloudflare cron 06:00 Manila, into the `prices` table. GOOGLEFINANCE is gone with the Sheet. **Nothing fetches a price on the read path.**
- **Status:** v1 (GAS + Sheets) ran v1.0.0→v1.9.2. `git show v1.9.2:CLAUDE.md` for the sheet-era lore; `git show v2.0.0:D1_MIGRATION.md` for the cutover plan.

## Deployment & triggers
- **Everything live is the Worker.** `npm run release` = D1 migrations → `wrangler deploy` → tag → push → GitHub Release. A UI-only change still needs the deploy; a GAS change needs `npm run push` and nothing else (no deployment exists to redeploy).
- **Worker secrets** (Cloudflare only): `APP_PASS`, `SECRET_TOKEN`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_USER_ID`, `GEMINI_API_KEY`, `INGEST_TOKEN`, `IBKR_FLEX_TOKEN`, `IBKR_FLEX_QUERY_ID`. `worker/.dev.vars` (gitignored) holds the same names for `wrangler dev`. **`GAS_URL` is deleted.**
- **GAS script properties:** `WORKER_URL`, `INGEST_TOKEN`, `GMAIL_HINTS`, optional `GMAIL_QUERY`, plus the machine-written `GMAIL_LAST_TS` and `BACKUP_SHEET_ID`. Everything else was deleted or moved.
- **Settings that used to be script properties now live in the `meta` table** and are editable on the Admin screen: `monthly_income_php`, `usd_php_fallback`, `owner_email`, `ledger_first_year` (+ machine-written `data_version`, `tg_last_ids`).
- **Triggers:** Cloudflare crons `30 16 * * *` (interest) and `0 22 * * *` (IBKR prices) — in `wrangler.toml`, so they ARE in source now. Apps Script keeps two: `gmail_ingest` every 5 min, and `backup_run` nightly (install with `backup_install()`). **Cloudflare does not retry a failed cron** — `runCron` catches and Telegrams the owner.
- **Backups, three layers:** the nightly Apps Script pull into a spreadsheet, the Admin screen's per-table CSV, and D1 Time Travel (7 days, free).
- **Free-tier headroom:** static assets are unmetered; only `/api`, `/login`, `/tg` and the crons burn invocations — a few hundred a day against 100k. D1 usage is thousands of read rows and dozens of writes against 5M/100k. The 10ms CPU cap excludes I/O wait, and the dashboard's aggregation is pushed into SQL for exactly that reason.

## Decisions
- 2026-08-23 (**v2.0.0, the platform swap — code complete, NOT yet cut over; the owner-side runbook is HANDOFF.md**): **Google Sheets is replaced by Cloudflare D1, and the Telegram bot moved into the Worker.** This is the topology the 2026-08-22 entry below said was the only one that collects the win: the dominant cost was never the sheet read, it was the Apps Script invocation plus the mandatory `/exec` 302, so the only way to get it back is to delete GAS from the request path. Two things pinned the project to GAS in that analysis and both were solved rather than argued away — **`GmailApp`** by keeping a ~180-line courier in Apps Script that parses nothing and writes nothing (free OAuth to the owner's mailbox, no off-platform equivalent), and **`GOOGLEFINANCE`** by a nightly **IBKR Flex Web Service** cron into a `prices` table (all holdings are at IBKR, and price history is now an audit trail the Sheet never had). The third loss — the Sheet as an admin UI — is replaced by an **Admin screen**: a generic CRUD grid over a server-side table whitelist, no SQL console.
  - **The prime directive was that the `/api` JSON contract does not move.** Same `?action=` names, same argument names in the sheet's header casing (`Category`, `Amount (PHP)`), same `{status:'error'|'duplicate'}`, same `version` gate. Result: `worker/public/app.js` needed **no changes** outside the new Admin screen and the removal of the now-pointless `_v` stamp. `migrate/verify.js` captures a fixture per read route off live v1 and diffs v2 against it; **structural diffs are fatal, value diffs are for a human** (live FX and the GOOGLEFINANCE→IBKR price-source change legitimately move PHP figures on USD/Shares accounts — a PHP-only account that moves at all is a real bug).
  - **Money is integer micros** (native × 1e6), converted only at the API boundary. Exact sums, and the same column holds a fractional IBKR share quantity — a Shares row's amount always WAS a quantity in the sheet, so this is one representation, not two.
  - **`su_lock_()` + `cache_bumpVersion_()` collapsed into one thing:** every write puts its statements and `bumpStmt(env)` in the same `env.DB.batch()`. D1 batches are transactional, so there is no lock to take, no bump to forget, and no window where a reader sees the write but the old version. `test.js` asserts every `ROUTES_WRITE` handler mentions `bumpStmt` — the successor to the old "must end with cache_bumpVersion_" rule.
  - **Two SQL traps, both hit while writing the schema.** ① A generated column may only call **deterministic** functions and SQLite registers the date/time family as non-deterministic (they can read `'now'`), so `strftime` in the `month` expression fails at CREATE TABLE time — it is `substr`/`CAST` arithmetic instead, and `test.js` asserts the JS `monthOf()` and that expression agree. ② **`ROUND` before `CAST`** in `amount_php_u`: CAST alone truncates toward zero, which negative amounts expose immediately.
  - **The KV edge read cache (v1.9.2) is deleted, one release after shipping it.** It existed to hide Apps Script latency and D1 is the thing it was faking; the namespace is rebound as `FX_CACHE`. The client-side `_v` stamp went with it (it would now be a cache-buster on nothing) — the behavioural test that guarded it is replaced by one asserting it is *absent*. `cachedCall`/`S.cache`/the version gate stay untouched: they are the offline story, not a latency trick.
  - **The webhook URL does not change and `setWebhook` does not need re-running** — Telegram already delivered to the Worker's `/tg`; it just stops forwarding to GAS. `/tg` still answers 200 first and works in `waitUntil`, because Gemini is slower than Telegram's patience, and the update-id claim is still needed (it stops the retry *storm*; the idempotent row id only stops the second *row*). It moved from CacheService to a `seen_updates` table — own table, not `meta`, so the admin grid and the nightly export stay free of churn.
  - **The ⌕ Email button survives** because the courier ships the 1200-char quote with the payload into an `email_quotes` table; the Worker cannot call GmailApp, and the alternative was dropping the feature.
  - **Deliberately NOT done:** a SQL console in the admin screen (that is `wrangler d1 execute` from the owner's machine); `transactions` insert/update in the grid (real handlers own validation and FX stamping, and the grid must not route around them — delete-by-id stays, for surgery); writing IBKR position quantities (the ledger stays the source of truth for how many shares are held, IBKR only prices them); a `visibilitychange` revalidation (still unbuilt, still not worth the invocations).
  - **Rollback for the first week:** the Sheet is frozen, not deleted, and v1.9.2 is one `git checkout v1.9.2 && clasp push` + a `wrangler rollback` away. D1 Time Travel covers data mistakes for 7 days; the nightly Sheets dump covers forever.
- 2026-08-22 (**phase 3 of the v1.6.0 plan, finally built — unreleased, needs the owner KV step below**): **`/api` reads are edge-cached in Cloudflare KV, keyed by `DATA_VERSION`.** Came out of an owner question — *would Supabase/Neon (then Render + UptimeRobot) be faster than Sheets?* Answer was **not for the reason expected**: swapping the DB under GAS moves ~200-800ms of a 0.5-2s round trip, because the dominant cost is the **Apps Script invocation + the mandatory `/exec` 302**, not the sheet read. The only topology that collects the win deletes GAS entirely — and `GmailApp` (no off-platform equivalent, `getMessageById` on trashed mail) plus `GOOGLEFINANCE` pin it there, so it would be a full backend rewrite for a personal tracker, and it would cost the Sheet-as-UI (hand-typing a BSP rate, adding a Ledger column). Render's free tier specifically: keeping it warm via UptimeRobot works but 750 instance-hours/month leaves **zero margin** (a 31-day month is 744), free cron isn't included so the interest job would ride the same keepalive, and Render+Postgres regions must both be Singapore or every query eats a transpacific RTT. **If the DB ever does move, the answer is Cloudflare D1, not Render+Neon** — same speed, on the Worker that already deploys, no keepalive, no third vendor. **What shipped instead** is the cheap layer: `gs()` stamps `&_v=<S.dataVersion>` on every read, the Worker keys KV on the whole query string. A write bumps the version → the next read asks a *different* key → a pre-write payload is unreachable, **so there is no purge logic and no TTL race**; and because every read handler stamps its own `version` into the payload, the key is only a bucket hint and can never be what decides freshness (a key/payload mismatch self-corrects on the next `getDataVersion`). **`getDataVersion` is deliberately never cached** — it is the oracle the entire client cache gates on, so caching it would make every other entry unfalsifiable and freeze the app on stale data; `cacheableRead()` is exported from `worker.js` **only** so `test.js` can guard that exception (mutation-tested: flipping the guard fails `npm test`). **The blocker that changed the design, and the reason not to "simplify" this back:** `caches.default` (the Cache API, which is what the phase-3 note in the v1.6.0 entry assumed) is a **documented silent no-op on a `.workers.dev` subdomain** — it needs a zone, i.e. a domain, the exact same wall that killed Cloudflare Access in v1.6.0. KV works there; it also survives a colo change, which the Cache API would not. **Honest ceiling, and it was worth saying out loud before building:** hit rate is modest, because the persisted `S.cache` already covers every repeat read on one device and a cold key at the client is cold at the edge too — this pays on the **second device**, a wiped client and post-Refresh, not on general navigation. `VER_TTL=3000` in `cachedCall` already suppresses the duplicate `getDataVersion` pings a re-render or a tab flip would cause, and `cachedCall` paints from cache *before* revalidating, so the revalidation latency was never user-visible anyway; the user-visible waits are **cold keys** (a never-visited month, a new `listTransactions` filter combo, a new device) and those are what this targets. **Unbound namespace = no caching and everything still works**, so the code deploy and the KV step need no coordination. TTL 600s; keys >400 chars skip (KV's key limit is 512B); `{status:"error"}` bodies (which GAS returns as HTTP 200) are never cached. **Owner step:** `cd worker && npx wrangler kv namespace create API_CACHE`, paste the id into the commented `[[kv_namespaces]]` block in `wrangler.toml`, uncomment, `npx wrangler deploy`. Until then this is inert.
  - **Bug found by the owner's smoke test the same day, fixed before release — the one failure mode a SHARED cache has and a private one cannot.** Device B showed a transaction logged on device A as stale for far longer than a moment. Cause: `gs()` gated the `_v` stamp on `S.dataVersion != null`, but `cachedCall` encodes *"I hold a version and do not trust it"* as **`fill(null)`** (`fill(verKnown() ? S.dataVersion : null)`), and `gs()` read the global and stamped it anyway. So an unconfirmed, pre-write version went into the KV key and pulled back **device A's own pre-write bucket** — data this client had already decided to distrust. Private per-device caching could never do this; the payload simply came from GAS and was fresh. Fix is one predicate: **stamp `_v` only when `verKnown()`**, i.e. never read a version-keyed shared cache while unsure what version you are on — no stamp means bypass means straight to GAS, the only honest answer. Guarded by a new behavioural test in `test.js` that runs **`app.js` itself in a `vm`** (it loads clean under four stubs) and asserts what `gs()` *builds*: stamped when confirmed, never when `_verAt` is 0 or older than `VER_TTL`, never on `getDataVersion`. Deliberately not a source-text check like `test_createIdempotencyGuard` — the bug was in the constructed URL and a grep for the old expression would have passed it. Mutation-verified: restoring `S.dataVersion != null` fails two cases. **Lesson worth keeping: the version gate was always two-valued (`known` vs `held`) and only the client had ever had to care; sharing the cache made the second value load-bearing across devices.**
  - **Not a bug, and the smoke-test step was written wrong the first time: there is no push.** Device B revalidates only when a `cachedCall` runs with `_verAt` past `VER_TTL` — i.e. on a navigation or re-render. A screen left open never updates itself, cache or no cache, and that is v1.2.x behaviour untouched by any of this. Post-fix expectation to test against: tap a screen on B → instant stale paint → `getDataVersion` → refetch → fresh, about two GAS round trips. If a *tap* still shows old data, that is a real bug. The upgrade if it ever matters is a `visibilitychange` revalidation (drop `_verAt` on resume) — a couple of lines, deliberately unbuilt, since polling a personal tracker to save one tap is not worth the invocations.

- 2026-08-17 (**phase 2, offline — shipped v1.6.1**; phase 1 shipped as **v1.6.0** the same day, both owner smoke-tested clean, incl. the airplane-mode offline check on device): **offline = cached shell + a queue for creates only.** `sw.js` caches the four shell files cache-first and **never `/api`** — the SPA already has a version-gated payload cache, and a second ungated HTTP cache in front of the data would serve stale figures invisibly; more importantly `gs()` must see the real network failure to queue. Reads needed no work (persisted `S.cache` + the swallowed revalidation failure already handled it). **Writes: `createTransaction`/`createTransfer` only.** They're the only idempotent-on-supplied-ID handlers, and they're what you actually do without signal (logging spend at a till); edits/deletes/account/Ledger writes refuse with an offline message — `api_appendLedgerRow` isn't idempotent at any price, and none of them are things you do away from a desk. `gs()` stamps `ui-<ts>-<rand>` as the ID **before the first attempt**, which is the whole safety property: the connection can die *after* GAS committed the row, so a replay must be recognisable — it comes back `{status:'duplicate'}` and counts as success. Guarded by `test_createIdempotencyGuard` (source-text check on both handlers + that `ID` is still in `TX_INPUT_COLS`). **Pending rows are derived from the queue** (`rebuildPending`), not tracked separately, so an offline entry is still on screen after a relaunch and disappears on sync. **Two bugs found by reasoning/testing rather than by the happy path:** ① a flush that hit a 401/expired cookie/cancelled prompt would have treated it as a server rejection and **deleted queued transactions** — inverted so a queued write is discarded *only* on an explicit GAS `{status:'error'}` (`_server`), everything else keeps it and stops the run; ② boot fires several `/api` calls at once, so one lapsed cookie produced a **stack of passphrase prompts** — `unlock()` now shares one in-flight promise. **Verified in a real browser** against `wrangler dev` with `fetch` stubbed to reject exactly as a browser does offline: create→queued, reads/updates reject without queueing, repeated flushes while offline never duplicate, garbage upstream keeps entries, explicit server reject drops one, and a `duplicate` reply syncs cleanly. **Could not verify locally:** service-worker install — the Claude browser pane blocks SW registration ("unknown error when fetching the script") even though `/sw.js` serves 200 `text/javascript` with `must-revalidate`; **owner confirmed it on device** after release, so don't re-investigate the local failure, it's the harness. **Known ceiling, deliberate:** nothing is version-keyed, so a deploy shows up on the *next* launch; the Refresh button clears the shell cache as the escape hatch, and the upgrade path (stamp the version into asset URLs from `release.js`) is noted in `sw.js`. Phase 3 (edge-caching reads keyed by `DATA_VERSION`) still deliberately unbuilt.
- 2026-08-17 (**phase 1, shipped v1.6.0**): **the frontend left GAS for the Cloudflare Worker, because offline is impossible inside `HtmlService`.** Owner's complaint was iPad/iPhone sluggishness + wanting offline with no mobile data. Diagnosis kept the two costs separate: the **shell** (a double-nested sandbox iframe, uncacheable, cold every launch) and **per-call latency** (a GAS execution reading a Sheet, 0.5–2s). Moving the shell fixes launch time, makes the persisted `S.cache` actually survive (the GAS sandbox origin rotates and wipes `localStorage` — the v1.5.4 persistence work was half wasted), and is the only way to get a **service worker** at all. It does **not** make `/api` faster; that's deliberate scope. **Cloudflare, and specifically the same Worker, is not a preference — the proxy is mandatory:** GAS can't send CORS headers and 302s every request, so something must front it regardless, and hosting on that same Worker makes the app **same-origin** with `/api` (no CORS, no preflight round trip on writes, one deploy). GitHub Pages/Vercel would mean two deploy targets and a preflight *adding* latency. **Auth = a passphrase checked in the Worker (`APP_PASS`), not Cloudflare Access:** Access is free for 50 users but only protects hostnames on a Cloudflare **zone**, i.e. it needs a domain, and the owner has none — swapping it in later deletes ~10 lines. Docs never said either way.
