- 2026-07-29 (**v1.3.1, same day — first live message exposed it**): **a retry storm; `CacheService` update_id dedup was NOT redundant.** First message logged correctly, then the bot replied "Already logged" over and over. Cause: the deterministic-ID dedup sits at the **create** step, i.e. *after* the Gemini call and the sheet reads, so a redelivery re-ran the entire slow path (~seconds), failed to answer Telegram in time exactly as the original had, and replied again — Telegram redelivers until it gets a timely response, so the loop fed itself. **Fix:** `tg_seen_(update_id)` claims the id in `CacheService` (1h TTL) at the **top** of `tg_webhook_`, before any work, and returns silently. **The two layers do different jobs and both are needed: the `tg-<update_id>` transaction ID stops a second ROW; the cache claim stops the retry STORM.** Claiming up front also means an execution that dies mid-way is not retried (you resend) — deliberate, noted in a `ponytail:` comment. Steady state now costs at most one wasted redelivery per message (fast no-op, no reply). Resolved same day — see the next entry.
- 2026-07-29 (**v1.3.2**): **Telegram will not talk to Apps Script directly; a Cloudflare Worker proxies it.** `getWebhookInfo` after a clean test (transfer logged correctly, exactly one reply) returned **`"Wrong response from the webhook: 302 Found"`** with `pending_update_count: 1`.
