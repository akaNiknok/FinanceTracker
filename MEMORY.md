## Project facts
- **What:** personal finance tracker. **Since v2.0.0 (2026-08-23) the backend is a Cloudflare Worker over Cloudflare D1.** Google Sheets is a frozen read-only archive, not the source of truth.
- **Cloudflare Worker:** `financetracker-telegram` (free plan) — serves the PWA, `/api` (D1), the Telegram bot at `/tg`, and one cron job (IBKR prices). **Never rename it:** `name` is the `.workers.dev` subdomain, i.e. both the app URL and the webhook target. Deployed from `worker/` with `npx wrangler deploy` (also run by `npm run release`).
- **D1 database:** `financetracker`, region `apac`. Schema in `worker/migrations/`. Money is **integer micros**; month keys are `yyyy-MMM`; balances are computed at read, never stored.
- **Apps Script ID:** `1IiUkd6dyJFnLuGXjjcS_CEohyeZLsXNO3eqFGm438IQL02dyhUxjgarE` (linked via `.clasp.json`). **No Web App deployment any more** — two trigger-driven files only (`Gmail.gs` courier, `Backup.gs` nightly dump). `GmailApp` is the sole reason GAS survives.
- **Frontend:** the PWA in `worker/public/` — 7 screens (Dashboard · Transactions · Budgets · Accounts · Swap · Tax · Admin), offline-capable since v1.6.1. The `/api` JSON contract did not change at the D1 cutover, so `app.js` was untouched apart from the Admin screen.
- **Locale:** PHP; timezone `Asia/Manila`. Every "today" goes through `manilaToday()` — Workers and D1 run in UTC.
- **Share prices:** IBKR Flex Web Service, Cloudflare cron 06:00 Manila, into the `prices` table. GOOGLEFINANCE is gone with the Sheet. **Nothing fetches a price on the read path.**
- **Status:** v1 (GAS + Sheets) ran v1.0.0→v1.9.2. `git show v1.9.2:CLAUDE.md` for the sheet-era lore; `git show v2.0.0:D1_MIGRATION.md` for the cutover plan.

## Deployment & triggers
- **Everything live is the Worker.** `npm run release` = D1 migrations → `wrangler deploy` → tag → push → GitHub Release. A UI-only change still needs the deploy; a GAS change needs `npm run push` and nothing else (no deployment exists to redeploy).
- **Worker secrets** (Cloudflare only): `APP_PASS`, `SECRET_TOKEN`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_USER_ID`, `GEMINI_API_KEY`, `INGEST_TOKEN`, `IBKR_FLEX_TOKEN`, `IBKR_FLEX_QUERY_ID`. `worker/.dev.vars` (gitignored) holds the same names for `wrangler dev`. **`GAS_URL` is deleted.**
- **GAS script properties:** `WORKER_URL`, `INGEST_TOKEN`, optional `GMAIL_HINTS`/`GMAIL_QUERY` (neither is set — `cfg_` falls back to the `GMAIL_HINTS_`/`GMAIL_QUERY_` constants in `Gmail.gs`), plus the machine-written `GMAIL_LAST_TS` and `BACKUP_SHEET_ID`. Everything else was deleted or moved.
- **Settings that used to be script properties now live in the `meta` table** and are editable on the Admin screen: `monthly_income_php`, `usd_php_fallback`, `owner_email`, `ledger_first_year` (+ machine-written `data_version`, `tg_last_ids`).
- **Triggers:** one Cloudflare cron, `0 22 * * *` (IBKR prices) — in `wrangler.toml`, so it IS in source now. Apps Script keeps two: `gmail_ingest` every 5 min, and `backup_run` nightly (install with `backup_install()`). **Cloudflare does not retry a failed cron** — `runCron` catches and Telegrams the owner.
- **Backups, three layers:** the nightly Apps Script pull into a spreadsheet, the Admin screen's per-table CSV, and D1 Time Travel (7 days, free).
- **Free-tier headroom:** static assets are unmetered; only `/api`, `/login`, `/tg` and the crons burn invocations — a few hundred a day against 100k. D1 usage is thousands of read rows and dozens of writes against 5M/100k. The 10ms CPU cap excludes I/O wait, and the dashboard's aggregation is pushed into SQL for exactly that reason.

## Decisions
- 2026-08-31: **the IBKR price poll retries every code IBKR calls transient, not just 1019.** The 06:00 job died with `Flex GetStatement error 1020: Invalid request or unable to validate request.` **The token was NOT the problem**, and that is the diagnostic worth keeping: `SendRequest` had already returned a ReferenceCode, which it cannot do on an expired (1012), invalid (1015), inactive (1011), IP-blocked (1013) or unknown-query (1014) token. So a failure at `GetStatement` clears the annual-token-renewal suspect by construction — read WHICH step threw before touching Client Portal. Root cause is ours, not IBKR's: the poll retried `ErrorCode 1019` and threw on everything else, but IBKR's table has TEN codes ending "Please try again shortly" (1001, 1004-1009, 1018, 1019, 1021) — any of them cost a whole night of prices. **1020 is retried too**: it is the catch-all "could not validate", and since SendRequest just passed on this token, every code that needs a person is ruled out and what remains clears by itself. `flexRetryable` is the split; a code outside it fails fast AND carries its repair in the Telegram message (`FLEX_FIX`), because "1012" alone does not tell the owner to make a new token. Two smaller fixes ride along: **the first `GetStatement` now waits 2s** — IBKR allows one request per second per token and `SendRequest` had just spent it, so the old zero-delay first poll both raced generation and sat on the limit — and **`xmlTag` tolerates an attribute and trims**, since a padded code matches nothing in the retry set and an attributed tag reads as absent, which hides the code from the failure message entirely. Guarded three ways: a unit test over the whole documented table, a `flexWhy` test for the padded/attributed tag, and a **contract guard** that `pricesJob` branches on `flexRetryable` and not on a literal — the silent failure is that comparing against one code looks right and passes every morning the statement is merely slow. Both guards were proved to fail before being trusted. **Not done:** re-running `SendRequest` for a fresh reference code on 1017, and making the sleeps injectable so a test could drive the poll end-to-end — a 7s test to prove what the guard already holds.
- 2026-08-30: **a name that names an account resolves to it — case is not part of the key.** "Foodpanda for Berry / 413.52 Maribank" was refused with `Unknown Account: Maribank` while `MariBank` sat in the table. Root cause: `refs()` indexes accounts and categories in a JS object keyed on the exact name, so every write path did an exact, case-sensitive lookup; the Gemini parser is told to copy a name character for character out of VALID ACCOUNTS but echoes the sender's spelling instead, and **the prompt taught it to** — rule 13's own example wrote "Maribank" twice. The fix is three layers, deliberately, because each catches what the one behind it cannot. ① **`db.js` gains `nameKey()`, a case-insensitive index beside the exact one, and `resolveAccount`/`resolveCategory`** — exact match first, case-insensitive behind it, and an ambiguous key (two names differing only by case) resolves to nothing rather than a coin flip. All five call sites in `api.js` use them, so the SPA, the bot, the Gmail courier and a raw API call all behave the same. The handlers bind the resolved row's **id**, so the stored row carries the canonical name whatever the caller typed. Two follow-ons: `createTransfer` compares the resolved **rows**, not the strings, or a self-transfer slips through under two spellings; `updateAccount` matches on `id` instead of `WHERE name = ?`. ② **The prompt's wrong example is corrected** and rule 3 now says do not echo the message's spelling. ③ **`telegram.js resolveAccountName`** widens further at the bot boundary only: exact → case-insensitive → letters-and-digits-only ("mari bank") → unique substring, the same test `/balance` has always made. Passes 2-4 take **one** candidate; two candidates pass the name through untouched so `createTransaction` throws its usual error instead of guessing, and the last two need three characters. The receipt is built from the resolved args, so the reply shows what was really written. **Not done:** `COLLATE NOCASE` on the name columns — `refs()` builds JS maps, so the collation is never consulted; it would need a table recreate and still not fix the lookup. Fuzzy resolution stays out of `api.js`: the API contract keeps exact-name semantics for everything but case.
- 2026-08-30: **`develop` deploys to a staging Worker.** `[env.staging]` in `wrangler.toml` → `financetracker-telegram-staging.<sub>.workers.dev`, its own D1 (`financetracker-staging`), deployed by `.github/workflows/staging.yml` on every push to `develop`. Purpose: check a change from a phone before the release PR is merged. **What the wrangler docs cost an hour to pin down:** most keys ARE inherited into a named environment — `main`, `compatibility_date`, `assets`, `workers_dev`, and **`triggers`** — while **bindings are not** (`d1_databases`, `kv_namespaces`, `vars`). Both directions bite. `assets` being inherited means the SPA needs no repetition (an earlier note here claimed otherwise — wrong). `triggers` being inherited is the trap: without `[env.staging.triggers] crons = []`, staging runs the 06:00 IBKR job and the net-worth snapshot against its own database on its own schedule. `name` is inherited WITH a suffix (`<name>-<env>`), so there is no `name` key and the never-rename rule is untouched. `kv_namespaces` is deliberately NOT repeated — FX_CACHE is optional, so staging just fetches every time. **Secrets are per-Worker and staging needs exactly ONE, `APP_PASS`** — no bot, no courier, no cron means `SECRET_TOKEN`/`TELEGRAM_*`/`GEMINI_API_KEY`/`INGEST_TOKEN`/`IBKR_*` are all dead weight there. **One real hole closed:** `telegram()` checks the header only `if (env.SECRET_TOKEN && ...)`, so an UNSET token leaves `/tg` an open write endpoint on a public hostname — `[env.staging.vars] SECRET_TOKEN = "staging-has-no-bot"` (a var, not a secret: a deliberately wrong value) makes every real Telegram POST fail closed. **A contract guard in `test.js`** holds the two silent failures: a staging `database_id` equal to production’s, and a missing crons override; both halves were proved to fail before being trusted. **Seeding is `workflow_dispatch` + `reseed` only**, never automatic — seeding on every push would wipe half-finished test state; `seed.sql` DELETEs first, so it is its own reset. **Staging never gets the real ledger:** a second copy doubles the blast radius of a leaked passphrase, and the point is behaviour, not balances. **Separate workflow file from `ci.yml`** because the two need opposite concurrency policies — CI cancels a superseded run, a deploy must never be cancelled between "migrations applied" and "Worker deployed".
- 2026-08-30: **the CI/CD path is now merge-and-forget, and local dev needs no credential.** Six changes, one theme — remove every step a person had to remember. ① **The release approval is gone.** The `production` GitHub environment carried a `required_reviewers` rule, so the workflow paused for a click that approved nothing the `develop` → `main` PR had not already approved. The rules are cleared through the API; the environment stays for its Deployments log, and `release.yml` says so, because a repo setting is invisible in the diff. ② **The back-merge is automatic.** After a merge into `main`, `develop` is an ancestor of `main`, so a `backmerge` job fast-forwards it with `git push origin HEAD:develop`. It runs on every push to `main`, released or not, and independently of the release job — `develop` must catch up even when a deploy fails. ③ **`ci.yml`, the gate that was missing:** `npm test` ran only in the local push hook (which no cloud-session PR and no browser merge pass through) and in the release job, on `main`, while deploying. Now every PR and every push to `develop` is tested. One job on purpose — `test-api.js` already applies the migrations AND `seed.sql` to a real SQLite database, so a `wrangler d1 migrations apply --local` step would download wrangler to re-prove that. ④ **`main` is protected** (PR + the `test` check, `enforce_admins` off). **`develop` is deliberately NOT** — a required check there rejects the backmerge job's push, whose commit carries no check of its own. The cost is that a `feature/*` → `develop` PR cannot use GitHub auto-merge; an agent watches `gh pr checks` and merges. ⑤ **`stamp-version.js`** hooks npm's `version` lifecycle, so `npm version patch` writes `index.html`'s `brand-ver` span. It was hand-edited, and forgetting it failed the release in CI, after the merge. ⑥ **Rollback is written down** (README): `wrangler rollback` returns the code in seconds, migrations never go back, so a destructive migration and the code that needs it must be two releases.
- 2026-08-30: **`wrangler dev` is not gated, and `worker/seed.sql` fills it.** Two things stopped an agent from checking a UI change: `/api` demanded the passphrase, which no agent may type, and a fresh local D1 was empty because the only filler is `npm run dev:pull` (the real ledger, denied to agents, and unavailable to a cloud session). `worker.js` `isLocalDev` skips the auth check when the request host is `localhost`/`127.0.0.1` — **not a flag in `.dev.vars`**, because a flag has to be planted in every checkout and could be set on the real Worker by accident; Cloudflare routes to a Worker BY HOSTNAME, so a production request cannot arrive that way. `worker/seed.sql` (`npm run dev:seed`) is invented data shaped like the real database: same six subtypes, the real category taxonomy, a USD contract salary into Wise, Wise→IBKR growth funding, broker buys and one sale, a card that is paid off, a refund as a negative expense, a Period override, an orphan ledger row for the ⚠ warning, and two `nw_snapshots` that agree with the seeded ledger so the dashboard bridge's residual is near zero. **Dates are RELATIVE** (`date('now','start of month', mo||' months', …)`, clamped to today), so the app always opens on a populated month and the file never goes stale. `test-api.js` applies it to the real migrated schema, so a schema change that breaks the seed fails `npm test`. It DELETEs before it inserts — re-runnable, and it replaces a `dev:pull` in the same local database.
- 2026-08-29: **the release moved from the owner's machine into GitHub Actions, so a cloud session can ship.** A cloud session cannot run the old `release.js`, for two independent reasons, and only one is a policy: ① the GitHub proxy in an Anthropic-hosted environment enforces **push protection** — `git push` reaches only the session's current working branch, so `git push origin main --tags` fails mechanically, and it fails AFTER `wrangler deploy` has already gone out; ② cloud environments have **no secrets store** — the docs state that environment variables are readable by anyone who uses the environment, so a `CLOUDFLARE_API_TOKEN` cannot live there. That token is not a build variable: Workers-deploy plus D1-write lets the holder deploy a Worker bound to `DB` and read every transaction, so it is a full-data credential. **The fix moves the trigger, not the credential.** `.github/workflows/release.yml` runs on a merge into `main`; the token lives in GitHub repo secrets; `release.js` keeps only the half that needs no credential — check the bump, run the tests, open the `develop` → `main` PR. Merging ships. A push to `main` whose version is already tagged does nothing, which is what keeps the hotfix flow (merge first, bump second) working. Side effect the owner wanted: a release no longer needs the laptop. **Not taken:** a self-hosted environment, which lifts both blockers but means running release infrastructure for a one-person project. `npm run push` (Apps Script) stays manual for good — clasp needs interactive OAuth, which no cloud session can do.
- 2026-08-29: **worktrees get a generated dev port, not the committed one.** `.claude/launch.json` pinned `wrangler dev` to 8123, so two worktrees fought over it. The file is now gitignored and written by `npm run bootstrap` (`.claude/launch.example.json` is the committed sample). The port is derived from the **checkout path**, not probed from what is listening: two idle worktrees bootstrapped the same day must still differ, and probing alone would hand both of them 8123. Bootstrap also runs `npm ci` and copies `worker/.dev.vars` in from the main checkout, the two other gitignored things a worktree does not inherit. It deliberately never runs `dev:pull` — that downloads real financial data.

- 2026-08-23 (**v2.0.0, the platform swap — cut over and live; the one-shot migration kit is deleted, see `git show v2.3.1:D1_MIGRATION.md`**): **Google Sheets is replaced by Cloudflare D1, and the Telegram bot moved into the Worker.** This is the topology the 2026-08-22 entry below said was the only one that collects the win: the dominant cost was never the sheet read, it was the Apps Script invocation plus the mandatory `/exec` 302, so the only way to get it back is to delete GAS from the request path. Two things pinned the project to GAS in that analysis and both were solved rather than argued away — **`GmailApp`** by keeping a ~180-line courier in Apps Script that parses nothing and writes nothing (free OAuth to the owner's mailbox, no off-platform equivalent), and **`GOOGLEFINANCE`** by a nightly **IBKR Flex Web Service** cron into a `prices` table (all holdings are at IBKR, and price history is now an audit trail the Sheet never had). The third loss — the Sheet as an admin UI — is replaced by an **Admin screen**: a generic CRUD grid over a server-side table whitelist, no SQL console.
  - **The prime directive was that the `/api` JSON contract does not move.** Same `?action=` names, same argument names in the sheet's header casing (`Category`, `Amount (PHP)`), same `{status:'error'|'duplicate'}`, same `version` gate. Result: `worker/public/app.js` needed **no changes** outside the new Admin screen and the removal of the now-pointless `_v` stamp. `migrate/verify.js` captures a fixture per read route off live v1 and diffs v2 against it; **structural diffs are fatal, value diffs are for a human** (live FX and the GOOGLEFINANCE→IBKR price-source change legitimately move PHP figures on USD/Shares accounts — a PHP-only account that moves at all is a real bug).
  - **Money is integer micros** (native × 1e6), converted only at the API boundary. Exact sums, and the same column holds a fractional IBKR share quantity — a Shares row's amount always WAS a quantity in the sheet, so this is one representation, not two.
  - **`su_lock_()` + `cache_bumpVersion_()` collapsed into one thing:** every write puts its statements and `bumpStmt(env)` in the same `env.DB.batch()`. D1 batches are transactional, so there is no lock to take, no bump to forget, and no window where a reader sees the write but the old version. `test.js` asserts every `ROUTES_WRITE` handler mentions `bumpStmt` — the successor to the old "must end with cache_bumpVersion_" rule.
  - **Two SQL traps, both hit while writing the schema.** ① A generated column may only call **deterministic** functions and SQLite registers the date/time family as non-deterministic (they can read `'now'`), so `strftime` in the `month` expression fails at CREATE TABLE time — it is `substr`/`CAST` arithmetic instead, and `test.js` asserts the JS `monthOf()` and that expression agree. ② **`ROUND` before `CAST`** in `amount_php_u`: CAST alone truncates toward zero, which negative amounts expose immediately.
  - **The KV edge read cache (v1.9.2) is deleted, one release after shipping it.** It existed to hide Apps Script latency and D1 is the thing it was faking; the namespace is rebound as `FX_CACHE`. The client-side `_v` stamp went with it (it would now be a cache-buster on nothing) — the behavioural test that guarded it is replaced by one asserting it is *absent*. `cachedCall`/`S.cache`/the version gate stay untouched: they are the offline story, not a latency trick.
  - **The webhook URL does not change and `setWebhook` does not need re-running** — Telegram already delivered to the Worker's `/tg`; it just stops forwarding to GAS. `/tg` still answers 200 first and works in `waitUntil`, because Gemini is slower than Telegram's patience, and the update-id claim is still needed (it stops the retry *storm*; the idempotent row id only stops the second *row*). It moved from CacheService to a `seen_updates` table — own table, not `meta`, so the admin grid and the nightly export stay free of churn.
  - **The ⌕ Email button survives** because the courier ships the 1200-char quote with the payload into an `email_quotes` table; the Worker cannot call GmailApp, and the alternative was dropping the feature.
  - **Deliberately NOT done:** a SQL console in the admin screen (that is `wrangler d1 execute` from the owner's machine); `transactions` insert/update in the grid (real handlers own validation and FX stamping, and the grid must not route around them — delete-by-id stays, for surgery); writing IBKR position quantities (the ledger stays the source of truth for how many shares are held, IBKR only prices them); a `visibilitychange` revalidation (still unbuilt, still not worth the invocations).
  - **Rollback for the first week:** the Sheet is frozen, not deleted, and v1.9.2 is one `git checkout v1.9.2 && clasp push` + a `wrangler rollback` away. D1 Time Travel covers data mistakes for 7 days; the nightly Sheets dump covers forever.

- 2026-08-10 (**shipped v1.4.0, deployment @60; `setupLedgerSchema` applied owner-side**): **Ledger rows reference a Salary transaction instead of duplicating it (issue #20).** Owner's real Ledger headers were `Date Received | Wise Amount | BSP Reference Rate | Total Income | Filed?`, so the migration adds only **two** columns — `Transaction ID` (FK → Transactions `ID`) and `8% Tax`. `Date Received`/`Wise Amount` become per-row `INDEX(MATCH())` lookups on tx `Date`/`Amount`; `Total Income` = `Wise Amount × BSP Reference Rate` (blank ⇒ 1); `8% Tax` = 8% of that. Typed cells left: `BSP Reference Rate`, `Filed?`. **Dropped from the first draft once the real headers landed:** `Description`, `Currency` and `Notes` columns — this ledger has never had them, the payout is always Wise/USD so `Currency` is constant, and `Ledger.gs` is header-generic so a hand-added `Notes` column would just work with zero code change. The deleted-tx warning moved onto `Date Received` (leftmost derived column) since there's no Description to carry it. **Per-row formulas, NOT ARRAYFORMULA** — ledger rows are appended/deleted one at a time and `api_deleteLedgerRow` does a real `deleteRow`, which would break a spill anchor. **`BSP Rate` is deliberately separate from the app's `ExchangeRate`**: BIR wants the central bank's reference rate on the date of receipt and the app has no feed for it, so it stays typed per row — that's the whole reason the manual column survives. **`Ledger.gs` needed zero changes**: its write guard is already `getFormula`-based, so the new derived cells are refused for free, and `api_appendLedgerRow` writes non-derived supplied columns, so "link a tx" is just `{Transaction ID: id}`. **Population = the issue's option (a), one-click, not auto-append on `api_createTransaction`** — no coupling of the tx write path to the tax sheet, and the owner stays in control of what gets filed; `api_getLedger` now also returns `unlinked` (Income: Salary tx no row points at) and the Tax screen renders them in a "Salary not in the ledger" card. Diff computed server-side, not client-side: one extra pass in an execution that already reads the sheet, and the join lives in one place. **Migration `setupLedgerSchema`** is additive (adds only missing columns, owner's extra columns untouched), backs the sheet up first, and **stamps formulas ONLY on rows it could link** — an unmatched legacy row keeps its typed figures rather than being blanked. Backfill matcher `mig_matchSalaryTx_` (pure, `test_matchSalaryTx`) links on date + |gross| and **returns null on ambiguity** (two same-day same-amount payslips) rather than guessing wrong into a tax filing. Deliberately NOT built: quarterly 2551Q/1701Q roll-ups (nothing consumes them yet), a per-quarter BSP reference table (rate is per-payslip), and a `deleteTransaction` guard for referenced rows — the Description formula falls back to `⚠ transaction deleted`, which is visible in the Sheet itself without coupling the two write paths.
